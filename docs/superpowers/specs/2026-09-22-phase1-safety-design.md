# LinYu 第一阶段安全修复设计

## 目标

以 `C:\Users\22763\Documents\linyu-open-source` 作为唯一源码仓库，清理重复且已废弃的工作目录，并修复三个影响用水状态安全的严重缺陷，同时不改变正常的登录、扫描、开关阀、小组件和账单行为。

## 范围

第一阶段包含四项交付内容：

1. 统一本地项目文件，删除可重新生成或已经废弃的内容。
2. 关阀失败或结果无法确认时，绝不向用户显示“使用结束”。
3. 独立监控每一台活跃设备，并在服务重启后恢复全部监控任务。
4. 防止退出登录时删除唯一的用水恢复上下文。

凭证明文降级、Release 日志脱敏、整体仓库重构、R8 规则、全部 Lint 警告和 CI 属于后续阶段。第一阶段只增加验证本阶段行为所必需的测试依赖。

## 关阀结果约定

继续使用现有 `CloseOutcome` 结果类型：

- `Closed`：按照现有服务端约定，关阀请求已被接受；可以清理本地状态并向用户报告完成。
- `Failed`：服务端明确拒绝关阀。必须保留或恢复活跃订单、计时、重试入口、小组件状态和失败通知。
- `Unconfirmed`：网络传输失败或结果不明确。状态处理与 `Failed` 相同，但使用“无法确认”的提示文案。

`ShowerWatchService.doFinish` 遇到 `Failed` 或 `Unconfirmed` 时，不得永久清除活跃上下文，也不得发送结算中或结束事件。App 与服务入口必须使用相同的结果映射规则。

## 多设备监控

将单一 `watchJob` 替换为由服务持有的 `MutableMap<String, Job>`。重复启动同一序列号时不创建新任务；启动另一序列号时新增独立任务。任务结束时只能移除自身对应的条目。

服务收到空 Intent 或因 `START_STICKY` 重启时，从持久化活跃订单中读取全部序列号，并为每一台设备恢复监控任务。只有在没有监控任务且没有正在执行的主动结束操作时，服务才能停止自身。设备名称、计时和通知操作必须按 `snCode` 读取，不能继续依赖全局 `lastDevice*`。

Android 对同一个前台服务只有一个前台通知位置。存在多个活跃订单时，第一阶段显示汇总前台通知；每台设备的完成或失败通知仍使用对应设备的内容和操作。

## 退出登录约定

只要持久化数据中存在任何活跃订单，就禁止用户主动退出登录。确认弹窗应提示用户先结束所有正在进行的用水。

被挤下线与主动退出不同，因为此时凭证已经失效。被迫退出时必须：

- 保留最小恢复数据，包括活跃订单、设备序列号、设备名称和开始时间；
- 停止已经无法认证的网络监控；
- 正确停止前台服务并移除其常驻通知；
- 明确提示设备可能仍在运行，并引导用户使用官方客户端或联系人工处理。

账号凭证和账号相关界面数据仍需清除。用户之后成功登录时，先用服务端状态核对保留的活跃订单，再决定是否删除。

## 测试设计

将关阀结果映射和退出登录判定提取为小型纯 Kotlin 函数，使本地单元测试不依赖 Android 运行环境。

必须覆盖以下回归场景：

- `Failed` 和 `Unconfirmed` 保留或恢复订单，并且绝不产生成功结果；`Closed` 才清除订单。
- 两个设备序列号可以同时注册；停止其中一个不能移除另一个。
- 服务重启规划会返回全部持久化活跃设备序列号。
- 存在至少一个活跃订单时，主动退出会被拒绝。
- 被迫退出会清除凭证，但保留恢复记录。
- README 不再引用 `svg2vector.py`。

每项行为都遵循红灯、绿灯、重构流程：先添加失败测试并确认失败原因正确，再编写最小实现，最后运行针对性测试和完整测试集。

## 验收方式

第一阶段只有在满足以下条件时才算完成：

- `testDebugUnitTest` 和 `assembleDebug` 通过；
- 使用迁移后的本机签名配置运行 `assembleRelease -x lintVitalRelease` 并通过；
- 针对性回归测试覆盖上述全部行为约定；
- Git 状态只包含有意修改的源码、测试和文档；
- 旧工作目录不再包含重复源码或带敏感信息的发布暂存文件。

现有 Lint 失败必须保留记录，不得通过建立基线静默隐藏。涉及本阶段修改代码的相关错误应一并修复，其余 Lint 清理留到质量门禁阶段。
